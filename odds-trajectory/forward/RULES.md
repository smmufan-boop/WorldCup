# 前瞻规则与门控规则 forward-rule-v1

登记日期 2026-10-13。前瞻起点为 **2026-10-13 12:00（北京时间）**，即该赛日开始。规则、门槛和评价方法均已固定，机器可读版本见 [`rule_spec.json`](rule_spec.json)。**任何参数改动都必须登记为新版本**，不能修改 v1 之后继续累计。

规则的依据见 [研究说明](../research/README.md) 中"以无模型规则为基础，用 V1 轨迹比对确认方向"和"借鉴人工分析的'门'"两节。另有两个并行记录的影子版本 **V1-四分之一** 和 **V1-多阶段**，见第 8 节。它们不改变 v1 的任何决策。

## 1. 方向规则（无模型）

只使用 Royal（公司 3）亚盘。取 **T−10**（开球前 600 秒）及之前最后一条有效赛前报价，清洗规则与 V1 的 `points` 相同：

| 盘口类型（让球数的小数部分） | 规则方向 |
|---|---|
| .25（平/半、半/一 等） | **受让方**：平局或差一档时赢半 |
| .75（半/一、一/球半 等） | **让球方**：恰好赢一球时赢半 |
| 整球、半球、平手 | **低水一方**；水位相同时选让球方，平手盘选主队 |

## 2. 门控规则

| 门 | 条件 | 说明 |
|---|---|---|
| **G_V1_T120** | T−120 的 V1 方向不为中性，且所指球队 = 规则球队 | V1 在 T−120 截点、用该截点的盘口计算：原分 D>50 指让球方，D<50 指受让方。比较的是**球队**而不是"上盘/下盘"，所以 T−120 到 T−10 之间让球方发生变化也能正确比较 |
| **G_V1_T10** | T−10 的 V1 方向缺失、中性，或所指球队 = 规则球队 | 只要 T−10 的 V1 不和规则唱反调即可 |
| **G_LINE** | 从初盘（第一条有效赛前报价）到 T−10，盘口朝规则球队移动 | 规则球队现在要让更多，或者受让更少（主队视角盘口变化 × 方向符号 > 0）；只看水位变化不算 |

V1 一律使用已发布的原版参数：Royal `p=2, α=20`，历史池要求开球 + 5400 秒早于截点、已核验 90 分钟赛果、主客队 ID 齐全。启动时会核对参数，与登记不一致则拒绝运行。

## 3. 信号等级

| 等级 | 条件 | 用途 |
|---|---|---|
| L0 | 方向规则 | 对所有可用比赛都记录，作为对照 |
| L1 | L0 + G_V1_T120 + G_V1_T10 | 次要检验 |
| **L2（主规则）** | L1 + G_LINE | **前瞻主检验对象** |

- 每场**真实比赛**只记录第一次 T−10 决策，之后不追加、不覆盖。同一场比赛有多个来源 ID 时，按 V1 的比赛身份键（主客队 ID + 北京时间日期）去重，保留最小的来源 ID。
- T−120 的 V1 结果在 T−120 到 T−10 之间计算并冻结；如果错过，就在决策时按 T−120 截点补算，并标记为 `recomputed_at_decision`。
- 开球后才生成的决策标记为 `late`，不进入评价。

## 4. 结算与评价

- **结算**：使用冻结的球队、盘口和该队水位（T−10 那条报价），按已核验的常规 90 分钟比分（含补时，不含加时和点球）结算。
- **赢盘率**：(全赢 + 赢半) / (全赢 + 赢半 + 输半 + 全输)，走盘剔除，与模拟投注页口径一致。
- **基准与提升**：按盘口类型分组的价格模型给出"预期赢盘率"，系数已在 2–7 月开发段固定，写在 `rule_spec.json` 中。提升 = 实际 − 预期，用来排除四分之一盘对赢盘率的天然影响。
- **主假设**：在前瞻、非迟到的决策中，L2 赢盘率高于同期 L0。
- **次要指标**：L2 相对基准的提升 > 0、按冻结水位计算的 L2 ROI、L1 对 L0、一级赛事子集。
- **检查点**：L2 已结算 150 注、300 注时各汇报一次。期间不修改任何参数。

## 6. 运行

只需 Python 3.10+、numpy、pandas。数据源可以是还原后的快照 SQLite（`--db`），也可以是本地 Pankou 的实时库（表结构相同），或者快照目录（`--snapshot`）。

```bash
# 每 5 分钟运行一次（例如用计划任务）：冻结 T−120/T−60/T−30 的 V1，并在 T−10 出决策
python odds-trajectory/forward/forward_rule.py scan --db PATH/TO/daqiu_odds.sqlite3 --ledger forward-ledger.jsonl

# 结算并汇报（随时可运行，结果不改写台账）；--list L2 逐场列出，--list-csv 另存表格
python odds-trajectory/forward/forward_rule.py settle --db PATH/TO/daqiu_odds.sqlite3 --ledger forward-ledger.jsonl --output forward-report.json --list L2 --list-csv l2.csv

# 历史参考
python odds-trajectory/forward/forward_rule.py backtest
```

- `scan` 以只读方式打开数据库，只追加写台账。每次运行会重建 T−10、T−30、T−60、T−120 四个截点的历史池（T−30 和 T−60 供影子版本使用）。
- 第一次 `scan` 时，已经过了某个冻结截点但还没到 T−10 的比赛，会在 T−10 按该截点补算（标记 `recomputed_at_decision`）。
- 台账每条决策包含：冻结报价、各截点的 V1 原分和有效样本、输入特征哈希、各门是否通过、影子版本是否下注、生成时间。
- `--now` 和 `--until` 只用于回放测试。回放测试已用快照的 10-12 晚间数据验证：64 场有历史记录的比赛，决策与 `backtest` 完全一致。

## 7. 局限

- 采集延迟或补采会影响"当时是否已有该报价"。`scan` 只能使用运行当时库里已有的数据，所以请确保采集程序在 T−10 之前已更新到最新报价。
- 一天能通过 L2 的比赛约 2–6 场，达到 150 注需要 1–2 个月。
- 欧指和大小球类的门要等采集到这两个市场后，作为新版本单独登记。

## 8. 影子版本：V1-四分之一、V1-多阶段

登记于 2026-10-13 14:13（北京时间），**前瞻起点为 2026-10-14 12:00**，即登记后的第一个赛日开始。定义写在 [`shadow_spec.json`](shadow_spec.json)。两个版本使用与 v1 相同的决策时点（T−10）、冻结报价和结算方式，在同一条台账决策中记录是否下注，**不改变 v1 的任何结果**。

| 名称 | 条件 |
|---|---|
| **V1-四分之一** | v1 的 L2，并且 T−10 盘口是四分之一盘（.25 盘买受让方、.75 盘买让球方） |
| **V1-多阶段** | 四分之一盘；盘口朝规则球队移动（G_LINE）；T−120、T−60、T−30 三个截点中至少 2 个的 V1 指向规则球队；T−120、T−60、T−30、T−10 中没有任何一个截点的 V1 指向对方 |

- 每个截点的 V1 都用该截点自己的盘口判断方向（D>50 指让球方）。没有方向、中性或无法计算，都算"无方向"。
- V1-多阶段**不要求 T−120 一定同向**，只要三个截点中任意两个同向即可。所以它不完全是 L2 的子集。
- 评价方式：在同一批前瞻决策上，与 v1 的 L2 和 L0 比较赢盘率（全赢 + 赢半算赢、走盘剔除）、相对基准的提升和 ROI。已结算 150 注、300 注时各汇报一次。
- 来源说明：V1-四分之一来自 10-09…10-12 复盘之后的研究；V1-多阶段是在探索过程中挑出来的，可信度低一档。
